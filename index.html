--- OVERVIEW

What is PHP2Shell?

PHP2Shell refers to CVE-2026-109618 and CVE-2026-109619, two pre-authentication RCE flaws in the PHP core session upload progress mechanism. The vulnerability was disclosed prematurely and carries a CVSS v4.0 score of 9.2 (Critical).

CVE-2026-109618 — OOM Corruption

An out-of-memory condition where a longjmp() call corrupts the Zend engine state. When memory limits are exceeded during multipart upload processing, the engine jumps to an error handler while leaving dangling references in the session HashTable. This enables arbitrary code execution without any application-level bug — a zero-dependency pre-auth RCE against any Apache mod_php installation.

CVE-2026-109619 — Use-After-Free

The RFC 1867 upload handler in ext/session/session.c stores raw zval* pointers into the session's HashTable for tracking upload progress. When an upload pauses beyond the minimum frequency threshold, a subsequent event reinitializes the session and calls zend_array_destroy(), freeing the array while cached pointers remain. Later writes dereference freed memory — a classic heap use-after-free leading to code execution.

ext/session/session.c — php_session_rfc1867_callback() ROOT CAUSE
1// RFC 1867 upload-progress callback caches a raw pointer
2ZVAL_LONG(&tmp, 0);
3zend_hash_str_update(Z_ARRVAL_P(post_bytes_processed), ..., &tmp);
4// ← cached zval* now lives inside the session HashTable
5
6// ... client stalls the upload for > 1 second ...
7
8zend_array_destroy(Z_ARR_P(session_vars));
9// ← arData is freed, but post_bytes_processed still points at it
10
11ZVAL_LONG(post_bytes_processed, new_bytes);
12// ← write through a dangling pointer → heap corruption → RCE
What happens, step by step The three-stage attack primitive behind both CVEs
1Arm

A multipart POST carries a session id plus an upload-progress field. The handler stores raw zval* pointers into the session HashTable.

2Free

The connection pauses past the minimum-frequency threshold, so PHP re-initialises tracking and frees the underlying array — leaving the cached pointers dangling.

3Execute

Further file chunks on the same socket write through those stale pointers. A 256-byte-filename heap spray lands the freed bucket under attacker control, turning the write into code execution.

--- AFFECTED VERSIONS

Who is Vulnerable?

PHP versions from 5.4.0 (2012) through 8.5.11 are affected. That is over a decade of PHP releases. End-of-life branches (8.1 and older) have no official vendor patch.

--- EXPLOIT CHAINS

Five Independent Attack Paths

Researchers have identified five distinct exploitation chains. Three are fully public. Two require additional prerequisites. All achieve remote code execution.

Chain A Public PoC

Session Upload + LFI

Injects code via upload filenames combined with local file inclusion. Requires pre-authentication and an LFI sink in the application.

Source: ikow/php2shell-poc (1.5k ★)

Chain B Public PoC

UAF Handler Overwrite

Overwrites handlers using a variable destruction use-after-free flaw. Needs an unserialize() call reachable in the application. Runs directly on the target.

Source: ikow/php2shell-poc (1.5k ★)

Chain C Public PoC

Serialization Handler Mismatch

Abuses mismatched serialization handlers across directories to trigger destructor methods on FPM workers. Leverages stale background states between requests.

Source: ikow/php2shell-poc (1.5k ★)

Chain D Restricted

Zero-Dependency OOM RCE

Described as "zero-dependency pre-auth RCE against any Apache mod_php installation." Relies on OOM corruption via longjmp() without needing any application-level bug. The most dangerous chain — no prerequisites beyond a vulnerable PHP version.

PoC requires paid access per the researcher's disclosure policy.

Source: ikow/php2shell-poc (1.5k ★)

Chain E Restricted

FPM Session Poisoning

Targets PHP-FPM by combining a session-starting endpoint with any consumer route, leveraging stale background states left between worker requests. Exploits the leftover global variables between worker requests to trigger use-after-free conditions.

PoC requires paid access per the researcher's disclosure policy.

Source: ikow/php2shell-poc (1.5k ★)

UAF Primitive Public PoC

Heap Spray + Stale Pointer Write

The foundational primitive: a multipart POST with a progress identifier triggers the callback, which caches pointers. The connection stalls for >1 second, prompting re-initialization that frees the array. Additional file chunks force writes through stale pointers. Heap spray prepends dummy file parts with 256-byte filenames matching the freed bucket structure size.

Source: syrex1013/php2shell (111 ★) · 0x4148/php2shell-lab (23 ★)

--- REMEDIATION

How to Fix It

The README from ikow/php2shell-poc explicitly warns: "no INI setting fixes it" regarding the Zend engine OOM flaw. Upgrading to patched PHP releases remains the only complete solution. However, temporary mitigations reduce exposure.

⚡ Upgrade PHP (Only Complete Fix)

Apply the emergency patch: 8.2.35, 8.3.36, 8.4.27, or 8.5.12+. This is the only remediation that fully addresses the core engine memory corruption. Do not delay.

🛡 Disable Upload Progress

The fastest mitigation — blocking upload progress parameters in multipart bodies offers immediate relief since legitimate usage is rare:

+ Show php.ini mitigation 
; php.ini — immediate mitigation
session.upload_progress.enabled = 0
memory_limit = -1
fatal_error_backtraces = 0

🛡 EOL Backport (PHP 7.0–8.1)

For end-of-life branches, use the backported Docker images from mpyw/php-eol:

+ Show Docker commands 
# Pull patched EOL image
docker pull ghcr.io/mpyw/php-eol-cve-2026-109618-109619:7.4-fpm-bullseye

# Build locally
docker buildx build \
  --build-context patches=./patches \
  -t php-eol:7.4-cli 7.4/bullseye/cli

🛡 WAF Rules

Deploy the ModSecurity rules above, or use Cloudflare WAF custom rules to filter malicious multipart traffic. For FrankenPHP, disable the mechanism globally via Caddyfile configuration blocks.

🛡 Nginx Request Buffering

Keeping nginx request buffering enabled prevents the necessary stall from reaching the FPM process — an additional defense layer that disrupts the timing-dependent exploit primitive.

🛡 Network Segmentation

Restrict access to PHP-FPM/CGI ports to trusted load balancers only until patched. Disable expose_php = Off in php.ini to prevent version leakage via HTTP headers.

Technical Analysis

  • Heap UAF in php_session_rfc1867_callback() — raw pointer caching in session HashTable
  • OOM longjmp() corruption — Zend engine state corruption on memory limit exceed
  • Heap spray technique — 256-byte filename strings matching freed bucket structure
  • ASLR bypass chain — cookie-based heap base leak + serialization alignment for library offsets
  • Command size limitation — inline payloads max 14 bytes (MAX_CMD = 14), longer commands need chaining
  • Worker rotation — abort current worker for predictable heap state before exploitation
